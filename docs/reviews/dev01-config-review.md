# DEV-01 configuration review

**Review target:** `d5bf1e8cf333e995bbf66820bd10201edf77140a`  
**Scope:** `unity/Assets/ELTS/Config`, shared configuration schemas, staging,
and the supplied configuration console checks. No production progress artifact,
hardware, calibration, or study acceptance was edited or claimed.

## Verdict: request changes before DEV-01 acceptance

The loader has a strong fail-closed baseline: it verifies staged-file and schema
hashes, rejects duplicate/unknown JSON fields and non-finite values, constructs
read-only typed values, explicitly denies study readiness, and refuses physical
ELTS endpoints. Two concrete cross-layer failures remain: staging can publish a
bundle that the loader rejects, and the supplied console projects can run each
other’s executable depending on build order.

## Findings

| Priority | Location | Finding |
| --- | --- | --- |
| P1 | `tools/config/stage.py:99-106`; `unity/Assets/ELTS/Geometry/Geometry.cs:154`; `DevelopmentConfiguration.cs:186-190` | The Python stager accepts display edges using a relative perpendicularity tolerance of `1e-9`, while `ScreenPlane` rejects normalized axes above its absolute `1e-10` basis tolerance. A Python-valid, hashed synthetic bundle can therefore fail during `DevelopmentConfiguration.LoadDirectory`. Align the tolerance and formulation, or canonicalize the validated display basis once, then test stager-to-loader acceptance at the boundary. |
| P1 | `tools/runtime-tests/ConfigChecks.csproj`; `tools/runtime-tests/GeometryChecks.csproj` | Both projects share the same directory and default `obj/` and `bin/` paths. After running the required configuration then geometry commands, rerunning `ConfigChecks.csproj` printed `PASS: 43 geometry checks` rather than running configuration checks. This makes validation order-dependent and can falsely report configuration coverage. Give each project a distinct intermediate/output directory or separate their project directories; assert the expected executable/banner in automation. |

## Reproduction

For the first finding, an isolated copy of only `config/` and `schemas/` was
used. The display lower-left and lower-right remained unchanged; the
upper-left X coordinate was increased by `3.375e-10` m. This yields a
normalized edge dot product of `5e-10`:

- Python staging accepted it because its relative threshold was `1e-9`.
- The staged files and manifest hashes were freshly generated by `stage()`.
- The C# loader, compiled in a separate temporary MSBuild output path, rejected
  the same bundle with `Screen basis axes must be perpendicular`.

This is not a measured calibration case. It shows that a configuration declared
valid by the repository stager can be denied at startup without any file
corruption or hash mismatch.

For the second finding, the required configuration check first printed
`PASS: 30 configuration checks`, and the required geometry check printed
`PASS: 43 geometry checks`. A subsequent unchanged command targeting
`ConfigChecks.csproj` printed the geometry banner. Giving ConfigChecks explicit,
unique `BaseIntermediateOutputPath` and `OutputPath` restored the expected
30-configuration-check executable.

## Validation performed

- Bundled Python staging completed: `PASS: synthetic configuration validated and
  staged`.
- The supplied configuration command initially completed with `PASS: 30
  configuration checks`; the isolated-output rerun also completed with the same
  result.
- The supplied geometry command completed with `PASS: 43 geometry checks`.
- Reviewed schema parity for unknown/missing fields, duplicate keys, non-finite
  values, synthetic-only mode, zero logged prediction, calibration/rig identity,
  display index separation, portable data roots, and mock/null endpoints. I did
  not find a study-mode, calibration, or physical-endpoint enablement bypass in
  the reviewed synthetic loader.

## Remaining boundary

Coordinator remediation at `c444010`: staging and runtime now share the
dimensionless `1e-10` basis tolerance, with paired below/above boundary checks.
`Directory.Build.props` isolates each console project's intermediate and output
paths before SDK imports. Alternating runs produced 32 configuration checks,
43 geometry checks, then 32 configuration checks, all exit zero. The staging
suite ran nine tests: seven passed and two symlink creation cases were skipped
because this Windows host denied creating symlinks. Receipt:
`project-management/progress/evidence/BOOT.S017-remediation.json`.

This configuration loader intentionally accepts only synthetic, unmeasured rig
data and cannot establish study readiness. Its hash manifest detects accidental
bundle corruption; it is not an independent authorization mechanism for a
repository writer who can change the manifest and all staged files together.
That is acceptable for the current development-only lane only while privileged
study and calibration acceptance remain outside this loader.
